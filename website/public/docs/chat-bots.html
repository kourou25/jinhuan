群机器人接入文档

把通知发进指定群，或让你的服务接收群成员的指令并回复。

推送消息 运行示例 回调协议 排查

推送消息

  1. 用群管理员账号打开目标群的「成员与设置 → 群机器人」，填名称并安装。只做通知时，回调地址和指令可以留空。
  2. 保存签发的推送地址和推送 Token。每次安装仅绑定一个群，Token 在安装或轮换时显示。
  3. 使用推送地址作为请求 URL，并在 Authorization 中带上该 Token。下面的环境变量填写你拿到的实际值。
curl -fsS "$PUSH_URL" \
  -H "Authorization: Bearer $PUSH_TOKEN" \
  -H "Content-Type: application/json" \
  --data '{"text":"备份已完成"}'

首次成功返回 201，正文包含 message_id 和 group_id。同一次操作重试时可带相同的 Idempotency-Key，重复提交相同文本会返回原消息 ID。每个机器人每分钟最多发 30 条文本，每条最多 2,000 个字符。

运行能回复指令的示例

下载 Cloudflare Worker 示例。它可以直接部署为一个 Worker，无需额外依赖。

  1. 在 Cloudflare 创建 Worker，将下载的代码作为入口部署。把 Worker 的 HTTPS 源（协议、域名和可选端口）交给尽欢站长开通回调白名单。
  2. 在目标群安装机器人，展开「接收群里的指令」。回调填 https://你的-worker域名/webhook/jinhuan，指令填 doc, help, status。
  3. 在 Worker 的「变量和机密」里，设置变量 PUSH_URL 为该机器人的推送地址。把推送 Token 和回调签名密钥分别存为机密 PUSH_TOKEN 和 SIGNING_SECRET，保存并部署。
  4. 用群设置里显示的机器人账号，在群里发 @机器人账号 /help。机器人会回复可用指令。发 @机器人账号 /doc 获取文档链接，发 @机器人账号 /status 检查整个回调链路。未配置回调域名时，先联系尽欢站长开通。

一个示例 Worker 使用一套机器人凭证。轮换后同步更新 Worker 的机密。

回调协议

回调地址由接入方提供，负责接收尽欢发来的 HTTPS POST。群成员显式点名机器人并发出已注册的指令时才会投递。下面是一条 /status api 指令的请求正文。

{
  "type": "chat.command",
  "event_id": "1ee1f988-1300-4692-a0a2-dc04d925f91e",
  "installation_id": "c2f464f0-0df1-467c-9399-fd2809707230",
  "group_id": 42,
  "message_id": 581,
  "bot_username": "bot_012345abcdef",
  "sender_id": 123,
  "sender_username": "alice",
  "command": "status",
  "args": "api",
  "created_at": 1795507200
}
验签
用回调签名密钥字符串的 UTF-8 字节做 HMAC-SHA256，输入为 X-Jinhuan-Timestamp、一个点和原始请求正文。校验 X-Jinhuan-Signature 的 sha256= 值及时间窗口。X-Jinhuan-Event 对应正文的 event_id。
确认和重试
回调返回 2xx 表示接收成功。失败会重试，用 event_id 给自己的业务操作去重。
回群
向同一个机器人的推送地址提交 {"text":"服务运行正常","reply_event_id":"收到的 event_id"}，机器人会引用原消息回复。同一事件只能创建一条机器人回复。

排查

  • 推送返回 401 时，检查 Token 是否属于该推送地址、机器人是否暂停、凭证是否已轮换。返回 429 时稍后重试。
  • 收不到指令时，核对群里的 @账号 /指令、已注册的指令名和 HTTPS 回调路径，再到「群机器人 → 投递记录」看结果。回调应直接接收请求，使用重定向会导致投递失败。
  • 能发消息却无法开启回调时，请尽欢站长检查签名密钥和回调源白名单。站点签名密钥用于签发机器人的回调签名密钥，接入方只使用安装后分配给自己的密钥。
